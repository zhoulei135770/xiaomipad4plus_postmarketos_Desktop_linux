# 指纹的"天花板"分析：为什么原始路径拿不到指纹图像

> 2026-10-29 01:20，基于 Android 真值帧 + 内核代码的对比分析

---

## 1. 决定性证据：我们的采集和 Android 完全等价

用同样的统计方法对比：

| 数据 | 来源 | min | max | row_spread | col_spread |
|---|---|---|---|---|---|
| `fx0.bin` | **Android（指纹能用）** | 144 | 168 | 1.41 | 0.98 |
| `fx1.bin` | Android | 143 | 160 | 1.22 | 0.69 |
| `v10-x0.bin` | **我们的驱动** | 146 | 156 | 1.50 | 1.02 |
| `v10-x1.bin` | 我们的驱动 | 143 | 157 | 1.18 | 0.89 |

**统计上无法区分。**

⇒ 我们修好的 SPI 协议（哑字节 + 大端）、窗口、时序、读图命令 —— **全都是对的**。
我们拿到的原始帧和 Android 内核驱动拿到的，本质是同一份东西。

> ⚠️ **重要限定**：这些 `fx*.bin` / `frame*.bin` 是在 Android 上从**内核驱动的原始缓冲**里
> dump 出来的，**不是 HAL 的输出**。Android 上真正用来做指纹的图像，
> 是 TA 自己通过 `qsee_spi_*` 读的，内核驱动根本不参与。
> 所以这组对比只能证明"我们的驱动读得和 Android 的驱动一样"，
> **不能**证明"这颗传感器出不了图"。真正的事实是下面第 2 节。

## 2. 而且原始帧里没有可用的指纹信号

对原始帧做逐像素时间方差（同一手指按住、连续多帧）：

```
fx0/fx1/fx2 逐像素标准差:  平均 0.75，最大 6.34
3 帧平均后:    min=147 max=159  row_sp=0.72  col_sp=0.42
10 帧平均后:   min=153 max=155（几乎完全平坦）
```

再把 `fx0` 拉伸对比度、去行均值后渲染成图（`build/gt/fx0-*.png`）——
看到的全是**横向条纹块**，没有任何脊线/谷线结构。

⇒ **原始缓冲 ≈ 常数 + 固定模式噪声。** 但这并不能说明传感器没用，
它只说明：**内核驱动走的这条"发 0xC0 再读 0xC4"的路子，拿不到成像结果。**

指纹图像是 FPC 的 TA 在 TEE 里自己通过 QSEE 的 SPI 接口读、自己算出来的
（TA 里确实有 `qsee_spi_open/read/write/full_duplex` 和整套 `fpc_sensor_hal_*`）。
**成像算法完全闭源，且运行在安全世界。**

## 3. 那能不能直接跑厂商的 TA？

### 3.1 有利条件

内核里**已经有** QSEECOM 支持：

```
CONFIG_QCOM_QSEECOM=y
drivers/firmware/qcom/qcom_qseecom.c
drivers/tee/qcomtee/          （可选）
```

我们手上也有全套 TA 二进制 + Android HAL：
`fpctzapp.mdt/b00..b07`、`vendor.qti.hardware.fingerprint@1.0.so`、`fingerprint.fpc.so`

### 3.2 但是有三道墙

**墙 1：主线 QSEECOM 不加载 TA，只连已经加载好的**

```c
/* List of supported applications. One client device will be created per entry,
 * assuming the app has already been loaded (usually by firmware bootloaders)
 * and its ID can be queried successfully. */
static const struct qseecom_app_desc qcom_qseecom_apps[] = {
	{ "qcom.tz.uefisecapp", "uefisecapp" },
};
```

它只调 `qcom_scm_qseecom_app_get_id()` —— TA 必须**已经**在 QTEE 里。
Android 是由 TEE 侧内核（qseecom）按需从 `/vendor/firmware` 加载的，
主线没有这个加载器。

**墙 2：`CONFIG_TEE` 没开**

```
# CONFIG_TEE is not set
```

所以 `qcomtee`（通用 TEE 框架）也没编进去。

**墙 3：HAL 要的是 Android 的 QSEECom ioctl ABI**

`fingerprint.fpc.so` 通过 `QSEECom_send_modified_cmd` 发命令 ——
那是 Android 的 `/dev/qseecom` 私有 ABI，主线的 qseecom 客户端设备不提供它。

### 3.3 理论上的完整方案（工作量很大）

```
1. 打开 CONFIG_TEE + CONFIG_QCOMTEE
2. 写一个 supplicant：把 fpctzapp.mdt/b0x 喂给 QTEE 加载（需 QTEE 接受签名）
3. 在用户态复刻 Android QSEECom 的 ioctl ABI（load_app / send_cmd / shared mem）
4. 把 vendor HAL（arm64 Android 库）跑起来 —— 需要 bionic 兼容层或重编译
5. 用 pmOS 的 /dev/fpc 中断和电源 GPIO 配合
```

**估计工作量：数周**，而且第 2 步能否成功取决于 QTEE 固件的签名策略（很可能拒绝）。

## 4. 现实建议

| 目标 | 可行性 | 建议 |
|---|---|---|
| 自己驱动芯片出指纹图 | ❌ 已证明不行（原始帧无信号，成像在 TA 里）| 放弃 |
| 跑厂商 TA（完整指纹功能）| ⚠️ 理论可行，工程量数周，成功率低 | 除非很有耐心，否则不建议 |
| **保留现状**：驱动能读原始帧、能做芯片自检 | ✅ | 作为"硬件已识别"的成果保留 |

### 4.1 已经拿到的实际价值

即使不追指纹功能，这一轮工作仍然有产出：

1. **FPC1020 的 SPI 协议被完全搞清楚了**（哑字节规则、大端字节序、命令表）
2. **TA 的反编译环境搭好了**（ARM32 + 多段 ELF + Ghidra，1513 个函数可读）
3. **驱动能完整控制芯片**：复位、唤醒、状态、寄存器读写、采集、图像读出
4. 这些对将来"跑厂商 TA"是必要的前置工作

### 4.2 如果将来要做 TA 路线，第一步是这个

```sh
# 打开 TEE 框架
CONFIG_TEE=y
CONFIG_QCOMTEE=m
# 然后看 qcomtee 能不能枚举到 QTEE 里的对象
cat /sys/class/tee/tee0/...
```

如果 `qcomtee` 能起来并且能拿到 QTEE 的服务列表，再考虑 TA 加载；
起不来就彻底没戏。

## 5. 一句话总结

> **指纹不是"驱动没写好"，而是"成像算法在闭源 TA 里"。**
> 我们已经把能自己做的部分（协议、时序、寄存器、采集）全部做对了 ——
> 证据就是：我们拿到的原始帧和 Android 拿到的，统计上完全一样。

## 6. 追加量化证据（自相关 + 交织假设检验）

### 6.1 二维自相关

对 `fx0.bin`（Android 原始帧，176×64，σ²=2.12，以均值为基准）：

| lag | 水平相关 | 垂直相关 |
|---|---|---|
| 1 | **0.81** | **0.02** |
| 2 | 0.81 | 0.04 |
| 4 | 0.78 | 0.04 |
| 8 | 0.74 | 0.03 |
| 12 | 0.74 | 0.03 |

> 复核（2026-10-29，用 numpy `corrcoef` 独立实现，扣真实均值）：
> `fx0.bin` 水平 lag1 = **+0.811**、垂直 lag1 = **+0.023**；
> 我们的 `v10-x0.bin` 水平 = +0.685、垂直 = +0.113。
> 两个独立实现结论一致。

**水平方向高度相关（平滑），垂直方向完全不相关（白噪声）。**

真正的指纹图像两个方向都会有连续的脊线，垂直相关应该在 0.5 以上。
这里等于 0 ⇒ 相邻两行在空间上**根本不是相邻的**，或者根本没有二维结构。

### 6.2 行交织假设被排除

既然行与行不相关，最自然的解释是"FIFO 里行是交织存放的"。
把行按 stride 重排（stride 1..16），再看垂直相关：

```
stride  1: +0.023      stride  8: +0.023
stride  2: +0.023      stride 11: +0.039   ← 最好也只有 0.04
stride  4: +0.023      stride 14: +0.039
```

**没有任何一种交织方式能让垂直相关变正。**

### 6.3 结论（更硬了）

> 这条读出路径拿到的数据：**每行是平滑的一维信号，行与行之间毫无关系**。
> 既不是二维图像，也不是"排错了的行交织图像"。

要成为指纹图，必须在读出之后做**传感器层面的重建**（多 ADC 组同步、逐列积分、
多次采样累加）。这套逻辑只存在于 TA 里。

## 7. 补充核实：**传感器是真的存在的**（前置）

一开始的怀疑是"这机型也许根本没装指纹"。查证后排除：

> "小米平板4 Plus 还支持**前置指纹解锁**与 AI 人脸解锁"
> —— [IT之家发布稿](https://www.ithome.com/0/376/666.htm)

所以：

- ✅ 硬件存在（前置，不是侧边电源键）
- ✅ SPI 通路上芯片有响应（状态寄存器会随命令变化：`0x0e` 空闲 → `0x1f` 采集后）
- ❌ 但内核驱动读出来的缓冲区里没有图像

⇒ 结论不变：**卡在 TA 的成像算法，不在硬件缺失。**
这对判断"还要不要投入"很重要 —— 不是"白费劲去驱动一个不存在的设备"。

### 7.1 顺带排除了"芯片被留在测试模式"

猜测：读出内容像测试图样（早期出现过 8 列块状结构），会不会 `ADC_TEST_CTRL (0x60)`
或 `IMAGE_SETUP (0x5C)` 的测试位被打开了？

查驱动源码：

- 我们的 v11 只写 `0x5C = 0x03 | 0x08 = 0x0B`（与 TA 的 `0x5C |= 8` 一致）
- **从来不写 `0x60`**，用芯片复位默认值（复位默认不会是测试模式）

⇒ 不是测试模式残留。这和"寄存器值本身不算错、但拿不到图"的判断一致。
