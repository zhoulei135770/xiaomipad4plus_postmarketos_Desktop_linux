## 1. 已经确定的事（不用重复验证）

| 结论 | 证据 |
|---|---|
| **0x54 = 0x00B00040** | TA 镜像里 10 处该常量（如 vaddr `0x6aec5`），与我们驱动一致 |
| **0x5C = 0x0B** | 脚本数据里 `5c 0b`，与驱动一致 |
| TA 用 **id 编号**体系 | id 表里出现 `0x1b` = `PXL_CTRL`（`FUN_00027fd4(3)` 查的 id）|
| 有 **dry/wet 两套脚本** | `aa 55` ↔ `55 aa`、`4c 04` ↔ `4c 00` |
| 地址映射 | 前两段 `vaddr = 文件偏移 − 0x1000`；seg2 之后要用程序头（`tools/ta_map_segments.py`）|

**这些已经写进 [25-TA-REVERSE-ENGINEERING.md](25-TA-REVERSE-ENGINEERING.md) §12–§14。**

## 3. 还没解的（就是这份备忘要交接的）

### 3.1 条目格式

数据从 `0x097c54` 开始，但**不知道每个条目怎么界定**。试过：

- `<寄存器地址><大端值><按寄存器宽度>` —— 走到 `0x02/0x2d/0x11` 这种不认识的号就断
- `<id><长度><值>` —— 长度对不上
- `<长度><id><值>` —— 同样断

线索：`0x0989b0` 那组是**独立的 id 数组和大小数组**（不是交错），
所以 `0x097c54` 的数据很可能也是"数组 + 数组"而不是"条目 + 条目"。

### 3.2 还没找到消费者代码

- 搜遍全镜像，**没有代码字面量**指向 `0x097c00`（表本身）
- 指向 `0x091300`（描述符）的字面量都在 b03 数据段（`0x0926ec`/`0x09272c`/`0x09276c`）
- 说明描述符表被**又一个结构**引用，链条还没走到 b02 的代码

### 4.3 换思路：从 id 表反查

`0x0999b0` 的 id 表里有 `0x1b`（PXL_CTRL）。
第 3 轮已经反编译过查 id 的函数：

```
fpc_sensor_hal_write_capture_setup
  → FUN_00027fd4(3)              # 取某种配置
  → 查 id 3 (ADC_SHIFT_GAIN)、id 0x1b (PXL_CTRL)
  → write_register_group (FUN_00027edc)
  → 每个寄存器走 FUN_00026090 → fpc1020_sensor_write
```

**顺着 `FUN_00027fd4` 反编译下去**，看它怎么把 id 变成值 ——
那条路大概率会走到 `0x097c54` 的数据。

```sh
sh /tmp/elf_func.sh 0x27fd4 250
sh /tmp/elf_func.sh 0x27edc 200
```

## 6. 2026-10-29 06:15 更新：调用链已经反编译出来了

本节替代 §4 里"顺着 FUN_00027fd4 反编译"的建议 —— **已经做完了**。

### 已解出（详见 [25](25-TA-REVERSE-ENGINEERING.md) §15）

- `fpc_sensor_setup_usecase(usecase)`：usecase < 12；查 id 3 / id 0x1b；
  只有 usecase 3 多写一段变长列表；最后统一 `0x5C |= 8`
- `lookup(handle, usecase, id)`：id 范围 0..0x25，usecase 0..0xb；两个配置源
- `get_settings()`：返回 `&DAT_0x90b80`，**镜像里是 0**，运行时才填

### 因此剩下的问题变成

> **谁在运行时把 `DAT_0x90b80` 填成什么？**

代码里没有字面量指向 0x90b80（只搜到两处指向 0x90b8c/0x90b8e，且在数据段），
所以静态定位不到写入方。

⇒ **再往下必须动态调试 TEE**，主线内核做不到。
⇒ **建议到此为止**，价值/成本比已经很差。
