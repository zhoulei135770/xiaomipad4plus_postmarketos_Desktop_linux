# 43 — 后摄成像链路：从"能拍到"到"看得过去"

- 日期：2026-10-29
- 结论：**硬件早已正常**（见 `CAMERA-FINDINGS.md`），画质的差距全部在 ISP 后处理。
  已把完整的 RAW 显影流程装进平板，拍照现在直接出 PNG。

---

## 1. 之前的状态

`tablet-cam` 只做两件事：自动曝光循环 + 保存 RAW10 原始帧。
转图依赖 PC 端的 `tools/raw10_to_png.py`，而那个脚本：

- 用 **2×2 合并**代替去马赛克 → 分辨率直接减半（2112×1568）
- 白平衡是简单的灰世界
- 用百分位拉伸代替色调曲线

结果就是：画面能看，但颜色偏、灰、发闷。

---

## 2. 新流程（`tools/raw10_to_png2.py`）

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 解包 | MIPI RAW10：5 字节 → 4 个 10bit | 总线格式 |
| 黑电平 | 减去实测基座 64，归一到 1023 | 不扣黑电平画面会发灰 |
| 去马赛克 | **Malvar-He-Cutler 5×5** 梯度校正线性插值 | 保留全分辨率 4224×3136 |
| 降噪 | 亮度中值混合（保边） | 高模拟增益下的彩噪 |
| 白平衡 | **Shades-of-Grey（Minkowski p=6）**，只在未饱和像素上统计 | 比灰世界更抗大面积单色场景 |
| 曝光 | `--exposure-ev` 线性增益 | 手动补光 |
| 色调 | 阴影提升 + 柔性肩部 | 手机感的关键；线性图又平又硬 |
| 传输 | sRGB 曲线 | 正确显示 |

### 2.1 参数

```sh
python tools/raw10_to_png2.py in.raw out.png \
    [--bin2]                 # 2x2 合并，快 4 倍，平板默认用这个
    [--exposure-ev 1.5]      # 提亮
    [--denoise 0.5]          # 0 关闭
    [--tone 0.7]             # 0 = 纯线性
    [--awb grey|sog]         # sog 默认
    [--scale 4]              # 输出缩小 4 倍（预览用）
```

PC 上 `--bin2` 约 1.9 秒，全分辨率去马赛克约十几秒。

## 3. 平板上直接出图

### 3.1 装了什么

```
/usr/local/lib/tablet-cam/develop.py     ← 转换器（就是 raw10_to_png2.py）
/usr/local/bin/tablet-cam                ← 抓完自动调用它
py3-pillow                               ← PIL 13.0.0（numpy 2.5.4 已有）
```

### 3.2 用法

```sh
sudo tablet-cam /tmp/photo.raw              # 抓 + 显影 → /tmp/photo.png
sudo tablet-cam /tmp/photo.raw --no-develop # 只要 RAW
```

实测：抓拍约 3 秒，显影 **15.5 秒**（2×2 合并，2112×1568），产物 7.7 MB PNG。

图形界面 `tablet-camera-gui` 走的是同一个 `tablet-cam`，所以按一次"拍照"就会得到
`/tmp/photo.png` 和 `/tmp/photo.raw` 两个文件。

### 3.3 为什么默认用 `--bin2`

全分辨率 Malvar 去马赛克在 ARM 上要几十秒、占几百 MB 内存。
`--bin2` 15 秒出图，日常够用；要最好的质量就把 RAW 拷到 PC 上跑全分辨率。

## 5. 还能继续提升的方向

| 方向 | 说明 | 难度 |
|---|---|---|
| **颜色矩阵（CCM）** | 现在没有相机色彩矩阵，颜色是"物理正确"而非"讨喜" | 需要标定（色卡） |
| **更好的降噪** | 现在是亮度中值，可换 bilateral / NLM | 中 |

## 7. Bayer 相位：实际是 BGGR，不是 GRBG（2026-10-29 16:20 修正）

### 7.1 怎么发现的

用户发来一张用手机拍的对照照片：桌上的盒子**是橙色的**，而平板成片里同一个盒子是**绿色的**。
这不是白平衡偏色，而是**通道错位**。

### 7.2 四个相位实测

用同一帧 `photo.raw` 分别按四种相位渲染（`--phase`）：

| 相位 | 盒子颜色 | 判定 |
|---|---|---|
| RGGB | 蓝色 | ✗ R/B 反了 |
| **BGGR** | **橙色（与实物一致）** | ✅ **正确** |
| GRBG | 绿色 + 彩虹条纹 | ✗ |
| GBRG | 绿色 + 彩虹条纹 | ✗ |

### 7.3 为什么格式字符串会误导

media-ctl 设的格式是 `SGRBG10_1X10`，字面意思是 GRBG。
但 **CSI-2 接收端/VFE 的相位对齐方式与传感器输出顺序可以不同**，
所以不能只看格式字符串，必须用已知颜色的实物验证。

**结论：这颗 OV13855 在本机的实际相位是 BGGR。**

### 7.4 顺带修掉的一个自身 bug

之前 `bin2` 实现用 `cfa[mask].reshape(h2, w2)` 取通道值。
布尔掩码按行优先展平时，**GRBG 相位下两个 G 采样点位于 (0,0) 和 (1,1)**，
在展平序列里并不相邻，于是 G 通道被错配成同一行的两个像素 → 彩虹条纹。

正确做法是按 **2×2 块**操作：

```python
blocks = cfa.reshape(h2, 2, w2, 2)
mb     = mask.reshape(h2, 2, w2, 2)
value  = (blocks * mb).sum(axis=(1, 3)) / mb.sum(axis=(1, 3))
```

这样对任何相位都成立。

### 7.5 仍未搞定的部分

**全分辨率 Malvar 去马赛克路径存在色彩 bug**：BGGR 下白平衡增益算成
`R=0.834 G=0.838 B=1.646`（2×2 路径是 `R=1.106 G=0.806 B=1.170`），
蓝色被过度放大，橙色盒子渲染成粉色。

说明通用化后的 `k_diag`（对角核）对 R/B 的填充有误。
**当前建议**：用 `--bin2`（2×2，颜色正确、速度快），全分辨率路径待修。

| 路径 | 颜色 | 速度 | 分辨率 | 状态 |
|---|---|---|---|---|
| `--bin2` | ✅ 正确 | 1.9 s (PC) / 15 s (平板) | 2112×1568 | **默认使用** |
| 全分辨率 Malvar | ❌ 偏粉 | 十几秒 | 4224×3136 | 待修对角核 |

### 7.7 复发：GUI 里的旧相位（2026-10-31 14:10 修复）

用户反馈"后摄色彩又不对了，橙色盒子拍出来是绿色"——**同一症状、同一个原因**：

- 命令行路径 `/usr/local/bin/tablet-cam` → `develop.py` 默认 `--phase BGGR`，是对的；
- **但 GUI `/usr/local/bin/tablet-camera-gui` 自带一份内联的取图代码**，
  写于 10-29 **09:24**（比 16:20 的 BGGR 修复早），仍按 **GRBG** 取平面：
  ```python
  # 旧：SGRBG10: (0,0)=G (0,1)=R (1,0)=B (1,1)=G
  g1 = img[0::2, 0::2]; r = img[0::2, 1::2]
  b  = img[1::2, 0::2]; g2 = img[1::2, 1::2]
  ```
  R/B 正好互换 → 橙色渲染成绿色。

**修复**（已部署）：

```python
# 新：BGGR: (0,0)=B (0,1)=G (1,0)=G (1,1)=R
b  = img[0::2, 0::2]; g1 = img[0::2, 1::2]
g2 = img[1::2, 0::2]; r  = img[1::2, 1::2]
```

- 备份：`/usr/local/bin/tablet-camera-gui.bak-grbg-1410`
- 启动项 `/usr/share/applications/tablet-camera-gui.desktop` 指向的正是被修的脚本；
- `python3 -m py_compile` 语法检查通过。

**教训**：相机有两条独立的显影实现（CLI 的 `develop.py` 与 GUI 的内联版），
改相位/白平衡时**必须两边都改**，否则会出现"命令行正常、GUI 偏色"的复发。
以后若再改色彩参数，先 `grep -rn "GRBG"` 全盘确认没有第二处。
